# 하네스 엔지니어링 정리

## 개요

하네스 엔지니어링은 **AI를 소프트웨어 개발에 안정적으로 활용할 수 있도록 실행 환경과 작업 절차를 설계하는 것**을 뜻한다.
최근에는 **에이전트 = 모델 + 하네스**라는 표현으로 설명되며, 여기서 하네스는 모델 바깥에서 AI가 실제로 일하는 방식을 통제하는 구조를 말한다. 이 표현은 Claude Code 등 실제 에이전트 도구에서 주로 사용하는 방식으로, 더 넓은 맥락에서는 오케스트레이션과 프롬프트 전략까지 포함하여 설명하기도 한다.

즉, 핵심은 모델 자체를 더 똑똑하게 만드는 것이 아니라,

* 어떤 문맥을 읽게 할지
* 어떤 도구를 사용할 수 있을지
* 어떤 검증 절차를 거치게 할지
* 어디서 멈추고 다시 시도하게 할지

를 설계하는 데 있다.

---

## 정의

하네스 엔지니어링은 **AI가 개발 업무를 일관되고 재현 가능하게 수행하도록 작업 환경을 구성하는 엔지니어링 작업**이다.

소프트웨어 개발 관점에서 보면, 단순히 프롬프트를 잘 작성하는 수준이 아니라 다음을 포함한다.

* 프로젝트 구조 이해 방식 설계
* 참조 문서 제공 방식 설계
* 실행 가능한 명령어 및 도구 제한
* 테스트, 린트, 빌드 등의 검증 루프 구성
* 실패 시 재시도 및 중단 조건 정의
* 작업 기록과 상태 관리 방식 설계

---

## 왜 중요한가

AI를 개발에 사용할 때 결과가 불안정한 가장 큰 이유는 보통 모델 자체보다 **환경과 절차가 정리되어 있지 않기 때문**이다.

예를 들어 단순히 다음처럼 요청하면 결과가 들쭉날쭉할 수 있다.

> 로그인 페이지 만들어줘

반면 하네스가 잘 설계된 환경에서는 AI가 다음과 같은 흐름으로 동작한다.

* 어떤 디렉터리에 파일을 생성해야 하는지 안다
* 어떤 라이브러리와 패턴을 써야 하는지 안다
* 참고해야 할 문서를 먼저 읽는다
* 구현 후 테스트와 린트를 실행한다
* 실패하면 로그를 바탕으로 수정한다
* 완료 조건을 만족해야 종료한다

즉, 하네스 엔지니어링의 목적은 **AI가 실패하지 않게 일하는 구조를 만드는 것**이다.

---

## 핵심 구성 요소

### 1. 컨텍스트 설계

AI가 어떤 정보를 먼저 읽고 참고해야 하는지를 정하는 작업이다.

예시:

* `README.md`
* 아키텍처 문서
* 코딩 컨벤션 문서
* API 명세서
* 디자인 시스템 가이드

중요한 점은 모든 정보를 한 번에 넣는 것이 아니라, **작업에 필요한 정보만 적절한 시점에 주입하는 구조**를 만드는 것이다.

### 2. 도구 설계

AI가 사용할 수 있는 명령어와 시스템 접근 범위를 정의한다.

예시:

* 파일 읽기/쓰기 허용
* `pnpm lint`, `pnpm test`, `pnpm build` 실행 허용
* 특정 디렉터리만 수정 가능
* 운영 서버 접근 금지
* 데이터베이스 조회만 허용, 변경 금지

즉, 하네스는 AI의 능력을 넓히는 것이 아니라 **통제 가능한 범위 안에서 일하게 만드는 장치**이기도 하다.

### 3. 검증 루프 설계

AI가 생성한 결과를 그대로 신뢰하지 않고 검증 단계로 다시 평가하는 구조를 만든다.

대표적인 검증 항목:

* 테스트 통과 여부
* 린트 오류 여부
* 타입 에러 여부
* 빌드 성공 여부
* UI 스냅샷 또는 E2E 테스트 통과 여부

단순히 통과/실패를 판단하는 것에서 그치지 않고, **실패 → 에러 로그 분석 → 수정 → 재검증** 의 자율 교정 사이클이 핵심이다. 이 구조가 있어야 AI는 단순 생성기가 아니라 **수정과 검증을 반복하는 작업자**처럼 동작한다.

### 4. 메모리와 상태 관리

긴 작업에서는 이전 결정사항과 중간 결과를 계속 유지해야 한다.

예시:

* 현재 작업 계획
* 이미 수정한 파일 목록
* 실패 원인
* 보류된 이슈
* 다음 단계 작업 내용

이런 상태 관리가 없으면 AI는 같은 실수를 반복하거나 작업 문맥을 잃어버리기 쉽다.

### 5. 샌드박스와 안전장치

AI가 위험한 행동을 하지 못하도록 실행 환경을 제한하는 설계도 중요하다.

예시:

* 운영 환경 접근 차단
* 시크릿 키 파일 접근 금지
* 배포 명령 실행 금지
* 승인 없이 대량 파일 변경 금지

이 부분은 단순한 보안 문제가 아니라, **AI 작업의 안정성과 예측 가능성을 높이는 핵심 요소**다.

## 개발 실무에서의 동작 방식

하네스 엔지니어링은 실제로 다음과 같은 흐름으로 구성된다.

### 1단계. 작업을 작은 단위로 분해

큰 작업을 그대로 던지지 않고, 작은 단위로 나눈다.

예시:

* 회원가입 API 추가
* 로그인 폼 유효성 검사 구현
* 사용자 목록 페이지 작성
* 테스트 코드 추가
* 문서 업데이트

작업 단위를 작게 나눌수록 AI는 더 안정적으로 결과를 낼 수 있다.

### 2단계. 프로젝트 규칙 문서화

AI가 따라야 할 규칙을 명확히 정리한다.

예시:

* React + TypeScript만 사용
* 상태관리는 Zustand 사용
* UI는 shadcn/ui 사용
* `any` 사용 금지
* 테스트 통과 전 완료 처리 금지

이 규칙들이 문서와 워크플로우에 녹아 있어야 일관성이 생긴다.

### 3단계. 기준 문서 지정

작업 시작 시 AI가 읽어야 할 문서를 정한다.

예시:

* `docs/architecture.md`
* `docs/coding-rules.md`
* `docs/ui-guidelines.md`
* `docs/api-contracts.md`

이 단계는 "무엇을 참고해야 하는가"를 명확히 하는 작업이다.

### 4단계. 실행 도구 체인 구성

AI가 작업 후 자동으로 검증할 수 있도록 명령 체인을 만든다.

예시:

```bash
pnpm lint
pnpm test
pnpm build
```

필요하면 Playwright 같은 브라우저 검증 도구도 포함할 수 있다.

### 5단계. 실패 및 중단 조건 정의

AI가 멈춰야 할 기준을 명확히 정한다.

예시:

* 테스트 실패 시 완료 금지
* 타입 에러가 하나라도 남아 있으면 실패
* 수정 파일 수가 너무 많으면 중단
* 설계와 다른 방향으로 변경되면 계획 재수립

이 조건이 있어야 AI가 무제한으로 수정하거나 폭주하지 않는다.

## 하네스 설계가 잘못되었을 때의 문제

하네스 자체가 잘못 설계되면 모델이 아무리 좋아도 결과가 불안정해진다.

| 잘못된 설계 | 발생하는 문제 |
|------------|--------------|
| 컨텍스트를 한 번에 너무 많이 주입 | 모델이 중요한 정보를 놓치거나 응답 품질 저하 |
| 검증 루프에 종료 조건 없음 | 실패가 계속될 때 무한 재시도 폭주 |
| 도구 권한을 과도하게 허용 | AI가 의도하지 않은 파일이나 시스템까지 수정 |
| 완료 조건이 모호함 | 작업이 끝났는지 판단을 못 해 불필요한 추가 작업 발생 |
| 실패 시 처리 방식 미정의 | 같은 오류를 다른 방향으로 반복하며 발산 |

즉, 하네스 엔지니어링의 목표는 AI에게 자유를 주는 것이 아니라 **올바른 제약과 절차 안에서 성공률을 높이는 것**이다.

## 예시 비교

### 일반적인 요청 방식

> 회원 목록 페이지 만들어줘

이 방식은 요구사항이 모호하고, 검증 기준도 없어서 결과 품질이 불안정하다.

### 하네스가 적용된 요청 방식

> 목표: `/users` 목록 페이지 추가
> 제약: 기존 라우터 구조 유지, shadcn/ui만 사용, 서버 상태는 React Query 사용
> 참고문서: `docs/frontend-architecture.md`, `docs/ui-guidelines.md`
> 검증: `pnpm lint && pnpm test && pnpm build` 전부 통과 필요
> 완료 조건: 목록 조회, 로딩/에러/빈 상태, 단위 테스트 포함
> 실패 시: 에러 로그 요약 후 한 번 더 수정

이 경우 AI는 단순히 코드 한 덩어리를 생성하는 것이 아니라, **정해진 개발 시스템 안에서 작업을 수행하는 실행 주체**가 된다.

## 개발자 관점에서의 의미

하네스 엔지니어링은 결국 다음 질문에 대한 답을 만드는 일이다.

* AI가 무엇을 읽고 시작해야 하는가
* AI가 어디까지 수정할 수 있는가
* AI가 어떤 도구를 실행할 수 있는가
* 결과를 무엇으로 검증할 것인가
* 실패하면 어떻게 다시 시도할 것인가
* 언제 완료로 인정할 것인가

즉, 이는 프롬프트 기술이라기보다 **AI 기반 개발 프로세스 설계**에 가깝다.

---

## 핵심 정리

하네스 엔지니어링은 **AI에게 일을 잘 시키는 기술**이 아니라, **AI가 제대로 일할 수 있는 개발 환경과 절차를 설계하는 기술**이다.

소프트웨어 개발자 기준으로 정리하면 다음과 같다.

* 프롬프트 작성보다 상위 개념이다
* 컨텍스트, 도구, 검증, 메모리, 제한 조건을 함께 설계한다
* AI의 자유도를 높이는 것이 아니라 성공률을 높이는 구조를 만든다
* 결과적으로 AI를 "자동완성 도구"가 아니라 "재현 가능한 개발 파이프라인의 일부"로 만든다

## 에이전트 구성 공식 (심화)

"에이전트 = 모델 + 하네스"는 하네스 엔지니어링의 핵심을 직관적으로 표현한 공식이다. 다만 실무에서는 아래처럼 더 세분화하여 이해하는 것이 정확하다.

```
에이전트 = 모델 + 하네스 + 오케스트레이션 + 프롬프트 전략
```

* **모델**: 추론과 생성을 담당하는 LLM
* **하네스**: 컨텍스트, 도구, 검증, 메모리, 안전장치 등 실행 환경 전체
* **오케스트레이션**: 여러 에이전트나 단계를 조율하는 상위 흐름 (멀티 에이전트 구조 등)
* **프롬프트 전략**: 작업을 어떻게 지시할지에 대한 설계 (시스템 프롬프트, few-shot 등)

하네스는 이 중에서 **실행 환경과 제약 조건**을 담당하는 핵심 레이어다.
